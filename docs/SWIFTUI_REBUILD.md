# Pennant for Mac: the SwiftUI rebuild

**Status:** design, 2026-09-25. Milestone N0 is done (2026-09-25: the restore point, the decisions D-055 to D-060 and
the D-052 amendment, the behaviour cases, the ground rules; section 12). Nothing else in this document is implemented yet. It supersedes the UI parts of the
V2 web plan (`~/.claude/plans/okay-can-we-please-effervescent-cherny.md`, sections 3 and 4). The server-side
parts of that plan (the Front Office contract, the Club Profile, the roster map, the horizon board, the league
wire, snapshots and the GM's desk) carry over unchanged in intent and are scheduled here.

**Owner decisions behind it (2026-09-25):**
- A full native SwiftUI rebuild, done as one big rewrite, with a guaranteed way back to today.
- It should feel like a native Mac app, with Liquid Glass. Deep, not superficial. Elegant to use.
- macOS 26 Tahoe is the minimum. The two users (the owner and his brother) are both on Apple Silicon Macs.
- The owner will join the Apple Developer Program for Developer ID signing and notarization.
- The React UI and Electron retire at cutover, in one final PR that is easy to revert.
- Restore point: tag `pre-swiftui` plus branch `archive/electron-react`, both at today's `main`.
- No postseason odds or buy/sell posture as headlines (they appear only in League Office standings, with their
  basis).
- League places are allowed for Player Value comparisons at a position (an amendment to D-052).
- AI gets slots only; the AI overhaul is a separate project.

Research inputs:
- Apple's HIG, WWDC25 and WWDC26 sessions, and the local Xcode 27.0 / macOS 27.2 SDK interfaces (Swift 6.4).
- The repository as of `87934cf`.

Every Apple API named below was checked in the installed SDK unless marked *unverified*.

## 1. The shape of the system

```
┌──────────────────────────── Pennant.app (Swift 6, SwiftUI, macOS 26+) ─────────────────────────────┐
│  Scenes: main window · player windows · club windows · compare · Settings · menu bar extra (opt.)    │
│  Features (local packages) ── PennantDesign (claims, glass, charts) ── PennantKit (models, stores)    │
│  PennantAPI  ← generated by swift-openapi-generator from contract/openapi.json                        │
│  ServerController (actor): spawns, watches, restarts, stops the sidecar                               │
└───────────────┬──────────────────────────────────────────────────────────────────────────────────────┘
                │ HTTP on 127.0.0.1:<random port>, bearer token per launch, SSE for events and chat
┌───────────────▼───────────── Contents/Helpers/node + Contents/Resources/server/*.cjs ─────────────────┐
│  The existing TypeScript server, unchanged in doctrine: import, Player State, Rights, Development,    │
│  Farm and MLB Ops, Player Value, calibration, AI. Plus a new presentation layer that authors every    │
│  sentence the app shows (Claims).                                                                      │
└───────────────┬──────────────────────────────────────────────────────────────────────────────────────┘
                │
   ~/Library/Application Support/ootp-front-office/   (the SAME folder the Electron app uses: D-049 hold)
   league.db · history.db · settings.json · config.json · …   + a data-folder lock + backups/
```

**Why this shape:**
- The server is Pennant's brain: 66,700 lines, with 37,200 lines of tests, every doctrine boundary test and all
  the calibration work. Porting it to Swift would throw away the thing that makes Pennant good. Keeping it also
  keeps D-001 ("the application decides; AI explains") and D-008 ("one domain API") intact.
- Only the part you see is rebuilt, and it becomes thinner than the React UI is today:
  - **the server writes every visible sentence** (section 4);
  - **Swift lays out, formats numbers, sorts, charts and integrates with macOS.**
- The research confirmed the server has no Electron dependency. It runs under plain Node once a small sidecar
  entry exists (section 5).

## 2. Design principles: deep, approachable, elegant

These are the tests every screen is held to.

1. **Four questions on the first screen.** Where are we? What are we good at? What are we bad at? What needs me?
   All answered with facts and stated places, never a thin prediction.
2. **The organization is the navigation.** Departments in the sidebar, each with a named head who "prepared"
   its report (staff from the save). Every function lives in exactly one department.
3. **Report → views → decision** in every department, generalizing D-043 and D-046. Detail grows as the GM
   drills down; nothing is hidden, and nothing is dumped.
4. **Depth is one gesture away, never in the way.** Four layers, mapped onto Mac conventions (section 3.3):
   glance, help tag, basis popover, inspector, workspace.
5. **Quiet by default.** One accent (the club's colour), glass only on the controls layer, content opaque and
   dense, numbers first. Colour is never the only signal: an SF Symbol and a word always go with it.
6. **Native all the way down.** Standard components, standard shortcuts, the menu bar, context menus,
   multiple windows, drag and drop, undo, Spotlight, widgets and notifications. Nothing that behaves like a web
   page.
7. **Motion means something.** Numbers roll when they change after an import (`.contentTransition
   (.numericText())`), glass morphs between toolbar states, and the inspector slides in. Nothing decorative.
   Everything respects Reduce Motion.
8. **Honest about uncertainty.** A range is drawn as a band with its most likely value marked. Thin evidence
   is hatched. Unknown is a short sentence, never a zero or a guess (D-018).
9. **Advisory, never a verdict.** Items are "to decide", "to review" or "watching", and link to the owner of the
   question. Nothing is ranked by a hidden score, and nothing writes to OOTP (D-004).
10. **It remembers, and the league is alive.** What changed since the last export, what the GM reviewed or
    deferred, and what the other 29 clubs did.

## 3. What the app looks like

A visual mockup (HTML imitation of the SwiftUI look) is at <https://claude.ai/artifact/5DHXS87be3FCP1aHfNhNAs>
(private until shared).

### 3.1 Scenes and windows

| Scene | API | Purpose |
|---|---|---|
| Main window | `WindowGroup(id: "main")` | Sidebar · content · inspector. Multiple main windows allowed (for example, one on Farm and one on MLB Ops) |
| Player window | `WindowGroup(for: PlayerRef.self)` + `openWindow(value:)` | One window per player card; restored at relaunch because the value is `Codable & Hashable` |
| Club window | `WindowGroup(for: ClubRef.self)` | Another club's scouting report (League Office) |
| Compare window | `WindowGroup(for: ComparisonRef.self)` | Two or more players, or us against another club, side by side |
| Staff room | `Window(id: "staff")` | The staff chat (existing AI, unchanged behaviour) as its own window; also reachable as an inspector tab |
| Settings | `Settings { }` | General (save and data folder, import), Appearance, AI providers and keys, Updates |
| Setup | `Window(id: "setup")` | First run: find the OOTP save, import, pick the club |
| Menu bar extra | `MenuBarExtra` (off by default) | Record, next game, desk count, "Open Pennant" |

The last route, the inspector's visibility, table column settings and open player windows are restored per
window (`@SceneStorage`, `TableColumnCustomization` is `Codable`, `.restorationBehavior`).

### 3.2 The main window

- **Sidebar** (`NavigationSplitView`; floats as glass automatically on macOS 26+):
  - The club card at the top: logo, name, record.
  - Departments, each disclosing its views. That's two levels, the HIG maximum for a sidebar.
  - A count badge of items "to decide" per department.
  - A **Following** section: clubs and players the GM follows (drag a player or club here to follow it).
  - Sidebar icons are SF Symbols.
- **Toolbar** (glass groups arranged with `ToolbarSpacer`):
  - Back and Forward, and the view title and subtitle (the date, and how current the data is).
  - Per-view scope controls (for example a level picker or a filter), with `.visibilityPriority` where space is
    short.
  - `.searchable` with tokens (`position:SS`, `club:SF`, `level:AAA`) placed top trailing.
  - An **Ask staff** button, and the inspector toggle.
  - Icons are monochrome. The club tint is used only for the one primary action where there is one.
- **Content:** opaque, grouped sections with concentric corners (`ConcentricRectangle`), dense tables with
  `.monospacedDigit()`, and Swift Charts.
- **Inspector** (`.inspector(isPresented:)`, `.inspectorColumnWidth(min: 280, ideal: 320, max: 440)`). It follows
  the selection, as in Finder and Xcode:
  - the **evidence** behind the selected figure or item;
  - the **player** summary when a player row is selected;
  - the **history** (what changed since earlier exports);
  - the **staff** tab: chat about the selection.

  Controls use `.controlSize(.small)`.

### 3.3 The four layers of depth, done the Mac way

The HIG gives a help tag to a *control* (one line, at most about 75 characters) and puts richer explanation in
a *popover* opened by a click. So Pennant's "hover to see why" becomes this:

| Layer | Gesture | What appears | API |
|---|---|---|---|
| Glance | Read | The headline or figure ("Hitting for power · 28th of 30") | `Text`, `.monospacedDigit()` |
| Hint | Hover | A one-line help tag, written by the server ("Team slugging against the other 29 clubs") | `.help(claim.hint)` |
| Basis | Click the figure or its ⓘ, or press **Space** on a selected row (like Quick Look) | A popover saying: **why** (evidence lines with values); **from** (department, specialist, as-of, sample); **how it's called** (calibrated, provisional or policy line); **not known**; **would change if**; **our philosophy's lean** with the neutral reading beside it. It can be **detached** into a floating panel and kept open while working | `.popover`, `.onKeyPress(.space)` |
| Evidence | **Pin** in the popover, or ⌥⌘I | The inspector shows the full trail: the evidence table, the players involved, thresholds with their stamps, related items, and history | `.inspector` |
| Workspace | "Open in …", double-click, or Return | The owning department's view or decision, or a player window | `openWindow`, `.contextMenu(forSelectionType:primaryAction:)` |

Every one of these is keyboard reachable. VoiceOver reads each claim's text as its label and its basis as custom
content (`accessibilityCustomContent`), so the depth is there without a mouse.

### 3.4 The Morning Report (Front Office)

1. **Masthead** (Apple Sports style). The club's colour band carries the record, division place and games back,
   run differential (with runs scored and allowed), the last five, streak, tonight's game with probable starters,
   and the trade-deadline date.
   - Numerals use SF Pro in a condensed width (`.fontWidth(.condensed)`) and roll on change.
   - It shows objective facts only: no odds, no posture.
2. **This week / since the last export:** chips that open their items (new, resolved, moved, recent results).
3. **How we win and lose.** Each dimension shows its league place on a 30-club strip, split into Strengths,
   Weaknesses and "the rest":
   - scoring runs, preventing runs, on base, power;
   - rotation, bullpen, defensive efficiency, baserunning;
   - recent against season.

   Each line is a claim. Policy lines are top and bottom fifth; below 20 games it reads "too early".
4. **Roster map.** A diamond of the regulars, with the rotation and bullpen beside it. Each position shows:
   - the holder, his Player Value band, and his league place at the position (with the overlap count);
   - the depth behind him, and the farm's next man with his readiness;
   - how long we control him.

   MLB Ops needs are marked on the nodes. It's drawn with Swift Charts and shapes. Clicking a node opens its
   evidence in the inspector.
5. **Your desk.** Items to decide from every department, merged and sorted by stated severity. Each names who
   raised it ("Raised by Jeff Banister, bench coach"). Statuses are Open, Reviewed, Deferred until…, and Handled
   in OOTP, with undo (`UndoManager`).
6. **Department reports.** Compact cards: department, head, summary line, 2–3 key figures and the top items.
   There's an empty staff-memo slot per card for the later AI pass.
7. **Around the league.** The top wire entries since the last export, with followed clubs first.
8. **Game day** (collapsible) and the **GM Briefing** (existing AI, collapsed).

### 3.5 One anatomy for every department report

Every report reads the same way:
- a masthead ("Prepared by {name}, {role}", data as of, a one-sentence summary);
- key figures;
- **To decide** and **Watching**;
- **What changed since the last export**;
- **What we can't see**: the department's unknowns, as short sentences. This makes the fog of war an honest,
  visible feature;
- the staff-memo slot.

The department's views sit beneath it in the sidebar.

| **Farm & Development** (minor league staff) | Report · Organization · Affiliates · Assignments · Prospects · Development tracking · Decision |
| **Scouting** (scouting director) | Draft board · Player search |
| **Trades** (assistant GM) | Trade desk (offers, builder, analysis, league fits) |
| **Finance** (front office) | Report · Payroll & budget · Contracts · Free agents · Horizon board |
| **Medical** (head trainer) | Report · Injury report |

### 3.6 Signature interactions

- **Drag and drop** (`Transferable` `PlayerRef` and `ClubRef`): drag a player from any table into:
  - the Trade builder;
  - a Compare window;
  - Following;
  - the Staff room ("ask about him").
- **Context menus** on every player and club: Open Card (double-click or Return), Open in New Window, Follow,
  Compare, Add to Trade, Copy Name, Show in Spotlight.
- **Command menus:**
  - **Go**: departments ⌘1–⌘9, Back ⌘[, Forward ⌘], Find Anything ⌘K.
  - **View**: Show Inspector ⌥⌘I, Show Sidebar ⌃⌘S, Basis for Selection (Space).
  - **Club**: Refresh Data ⌘R, Import Export…, Data Status.
  - **Player**: acts on the focused selection via `@FocusedValue`.
- **Search** with tokens and suggestions, across players, clubs, pages and actions.
- **Numbers that roll** when a new import lands, and a banner or notification: "New export read · 3 new on your
  desk".
- **The Trade builder** is a two-sided drop target. Swift Charts draws the value difference as ranges.
- **The Horizon board** is a grid of position × the next three seasons:
  - each cell shows who is controlled and how;
  - prospects sit in a pipeline lane with their readiness range, never placed in a season;
  - a committed-payroll line runs against a budget `RuleMark`.

### 3.7 Visual language

- **Liquid Glass** only on the navigation and controls layer: sidebar, toolbar, inspector, popovers, sheets,
  menus. Standard components get it automatically.
  - Custom glass is limited to a few floating controls (for example the roster map's filter), placed in a
    `GlassEffectContainer` with `glassEffectID` morphing.
  - Never glass on glass, and never glass on content.
  - macOS 27's refreshed glass and the user's transparency setting come for free. Reduce Transparency and
    Increase Contrast are tested on the custom pieces.
- **Colour:**
  - The club accent comes from server-resolved theme tokens: `derivePalette` moves server-side, so
    `npm run check:theme` keeps guarding contrast.
  - Semantic tones (good, bad, caution, neutral, unknown) are asset colours with light, dark and
    increased-contrast variants, kept distinct from rights colours.
- **Type:** SF system text styles; `.monospacedDigit()` in tables; condensed-width SF for scoreboard numerals
  (this replaces Oswald); no web fonts.
- **Icons:** SF Symbols throughout (licensed for Apple platforms), with emoji removed.
- **Shape:** concentric corners (`ConcentricRectangle`, `.containerConcentric`) and capsule glass controls.
- **Empty and unavailable states:** `ContentUnavailableView` with one plain sentence ("Not valued yet: his
  contract terms aren't in the export"). An unavailable department says so and never reads as "all clear".

## 4. The presentation contract: the server writes every sentence

Research found about a quarter of the prose the GM reads is authored in React today. This includes:
- label maps in `src/pages/mlb/common.tsx` and `src/pages/farm/common.tsx`, and `platoonCopy.ts`;
- word builders in `valueWords.ts`, `costBand.ts`, `productionConeGeometry.ts`, `dataStatusModel.ts` and
  Payroll's helpers;
- `glossary.ts`, the `stats.ts` catalog, and the Prospects recommendation words;
- Philosophy's `buildIdentity` and Development's "biggest movers".

All of it moves to the server, for three reasons:
1. The Swift app stays a thin, judgment-free renderer (D-001, D-008).
2. The plain-language rule stays enforced **once, in TypeScript**, over every string the app can show.
3. Two clients could never disagree during the transition.

### 4.1 Types (in `server/contract/`)

```ts
type Certainty = 'calibrated' | 'provisional' | 'policy' | 'unknown';         // open enum in the spec
interface Claim {
  text: string;                    // the visible line, GM voice
  hint?: string;                   // ≤ 75 chars, the help tag
  value?: { n: number | null; unit: Unit; low?: number; high?: number; display: string };
  tone: 'good' | 'bad' | 'caution' | 'neutral' | 'unknown';
  place?: { rank: number; of: number; tiedWith: number; overlap?: number };   // league places, stated
  basis: {
    because: Array<{ label: string; value: string }>;
    source: { department: DeptId; specialist: string; asOf: IsoDate | null; gameDate: string | null; sample?: string };
    unknown: string[]; wouldChange: string[];
    lean: { neutral: string; why: string[] } | null;        // explicit, never "absent means something"
    certainty: Certainty; stamp?: string;                    // D-041 stamp shown in the evidence view
  };
  links: Target[];                  // { kind: 'department'|'player'|'club'|'decision', … }
}
interface Row<T> { id: string; cells: Record<string, Cell>; sort: Record<string, number | string | null>; claim?: Claim }
interface Cell { display: string; tone?: Tone; hint?: string; claimRef?: string }
```

- **Tables arrive ready to show:** display strings, raw sort keys (null means unknown, sorted last in both
  directions), and claims where a cell has a basis.
- **Swift ports only presentation:** the unknown-last comparator, number formatting of served values, and chart
  geometry. The comparator's cases live in `contract/fixtures/sort-cases.json` and run in both Vitest and Swift
  Testing.

### 4.2 Endpoints

Everything new lives under `/api/v2/`, so the React app keeps working on the old routes until cutover.

| Endpoint | Purpose |
|---|---|
| `GET /api/v2/front-office/:org` | Masthead, profile, roster map, desk, report cards, wire top, changes |
| `GET /api/v2/departments/:org/:dept` | Full department report |
| `GET /api/v2/views/:org/:dept/:view?…` | One view's payload (tables of `Row`s, sections of `Claim`s) |
| `GET /api/v2/claims/:key` | The evidence trail on demand (for example an MLB need's staff recommendation, which takes about 3.6 s, so it is never in a summary) |
| `GET /api/v2/player/:id` · `/club/:id` · `/compare?…` | Dossier, club report, comparison |
| `GET/PUT /api/v2/desk/:org` · `GET/PUT/DELETE /api/v2/following` | The GM's desk and follows |
| `GET /api/v2/wire/:org?since&club&kind&followed` | Around the league |
| `GET /api/v2/catalog` | Glossary, stat catalog, theme tokens per club, department list and staff heads |
| `GET /api/v2/events` (SSE) | Import progress and finished, job progress, desk changes, freshness. This replaces 8-second polling |
| existing chat SSE, jobs, settings, import, trade analyze | Reused, and described in the spec |

### 4.3 The typed pipeline (no hand-written models)

1. **Source of truth:** the server's TypeScript types. `server/contract/routes.ts` lists every operation (method,
   path, operationId, params, response type, stream).
2. **Build:** `npm run contract:build` runs ts-json-schema-generator over `server/contract/index.ts` and writes
   **`contract/openapi.json`** (OpenAPI 3.1, committed). Two rules apply while building it:
   - Closed string unions are wrapped as *open enums*, so an older app build never fails on a new code.
   - OOTP game dates are a named `GameDate = string` alias with no format (they're unpadded; see AGENTS.md).
3. **Swift:** the `macos/Packages/PennantAPI` package runs Apple's **swift-openapi-generator** as a build plugin
   (types and client, URLSession transport, SSE decoding via `asDecodedServerSentEventsWithJSONData`). Its
   middleware adds the bearer token.
4. **Drift checks in Vitest:**
   - The committed spec equals a fresh build.
   - Every registered route is in the spec and vice versa (reusing `tests/routes.test.ts`'s route walk).
   - Every v2 GET's live response against the synthetic save validates with ajv (`unevaluatedProperties: false`).
   - **Every `text`, `hint` and `display` string in those responses passes the consolidated banned-jargon list**
     (`tests/bannedJargon.ts`, replacing the per-page copies).

   `swift build` of PennantAPI in CI fails on any breaking change.

## 5. The sidecar server

### 5.1 Server changes (small, additive)

- **Entry:** `server/sidecar.ts`, bundled by esbuild into `build/sidecar/server.cjs` beside the two refit
  workers. It has to be `.cjs` and sit in the same folder, because workers are found next to their caller
  (`playerValue.ts:1665`, `saveCalibration.ts:150`).
- **Port:** calls `startServer(0)`, which also fixes the `Number(PORT) || 5178` bug (a random port could not be
  requested). Once listening it prints one line: `PENNANT_READY {"port":N,"pid":…,"version":…}`.
- **Secrets over stdin:** reads one JSON line `{ token, keys: {…} }` from stdin, and exits on stdin EOF or when
  `process.ppid === 1`. macOS has no parent-death signal, and the stdin pipe closes even if the app crashes.
- **Shutdown:** a SIGTERM handler (none exists today) closes the HTTP server, stops the watcher, closes both
  databases and exits 0.
- **Bearer-token middleware** on `/api`, after the existing loopback Host check, with constant-time comparison.
  The server's own self-calls (`chat.ts:99`, `exporter.ts:111`) send the token too.
- **Always bind 127.0.0.1**, passed explicitly because a `.env` in the data folder could otherwise change the
  binding (`config.ts:36-48`).
- **Data-folder lock** `server.lock` (pid and start time). Both the Electron build and the sidecar take it, so
  the two apps can never write the same database at once.
- **Injected keys:** a key source beside `setSecretCrypto`. Keys live in the Mac Keychain and are handed over on
  stdin, never through environment variables (another process run by the same user could read those).

### 5.2 Inside the bundle (arm64)

| Path | Contents |
|---|---|
| `Pennant.app/Contents/MacOS/Pennant` | The Swift app |
| `Contents/Helpers/pennant-server` | The official Node 24 LTS binary, pinned by version and SHA-256, renamed so Activity Monitor reads well |
| `Contents/Resources/server/` | `server.cjs`, `value-refit-worker.cjs`, `calibration-refit-worker.cjs`, `package.json`, pruned production `node_modules` (better-sqlite3 built for Node's ABI, so the Electron ABI trap is gone) |

**Signing (inside out):**
1. Each `.node` file.
2. The Node binary, with hardened runtime, a timestamp, and only `allow-jit` and
   `allow-unsigned-executable-memory` (V8 needs these).
3. Sparkle's helpers.
4. The app last: hardened runtime, no JIT entitlements, **no App Sandbox**. A sandboxed Node child would need
   inherited sandboxing and security-scoped bookmarks for arbitrary OOTP save folders and the live `temp/` copy,
   with no benefit under Developer ID.
5. Notarize with `notarytool` and staple both the app and the DMG.

**Privacy prompts.** The child inherits the app's TCC responsibility, so prompts name "Pennant":
- Reading the Mac App Store OOTP container (`~/Library/Containers/…`) triggers "access data from other apps".
- Save folders in Documents, Desktop or iCloud trigger Files & Folders prompts. Info.plist carries the
  `NS…UsageDescription` strings.

A stable Developer ID signature means these prompts and Keychain prompts appear once, not on every update.

### 5.3 Lifecycle (`ServerController`, a Swift actor)

1. **Spawn** with these variables:
   - `OOTP_FO_DATA_DIR=~/Library/Application Support/ootp-front-office`
   - `OOTP_FO_APP_ROOT=…/Resources/server`
   - `OOTP_FO_APP_VERSION=<CFBundleShortVersionString>`
   - `OOTP_FO_BIND=127.0.0.1`
   - `OOTP_FO_EMBEDDED=1`

   Then write the stdin JSON line, wait up to 30 s for `PENNANT_READY`, and confirm with `GET /api/status`.
2. **Crash:** detected via `terminationHandler`. Restart with backoff (1, 2, 4 … 30 s). After 5 crashes in 2
   minutes, stop and show a `ContentUnavailableView` naming the data folder, with "Show Log" and "Try Again".
3. **Quit:** `applicationShouldTerminate` returns `.terminateLater`, then SIGTERM, a wait of up to 5 s, SIGKILL,
   and then reply. Whether an import killed halfway is transactionally safe must be verified in N1.
4. **Logs:** captured to `~/Library/Logs/Pennant/server.log` (rotated), viewable from Help ▸ Server Log.

## 6. Swift architecture

- **Project:**
  - `macos/Pennant.xcodeproj` using buildable (folder-synchronized) groups, so there is almost no project-file
    churn.
  - Swift 6 language mode, default actor isolation `MainActor`, Approachable Concurrency.
  - Deployment target macOS 26.0. APIs new in macOS 27 are used only behind `if #available(macOS 27, *)`.
- **Local Swift packages** (`macos/Packages/`):
  - **PennantAPI:** the generated client and types, plus the token middleware.
  - **PennantKit:**
    - `ServerController`;
    - `AppModel` (`@Observable @MainActor`): server state, current club, freshness, import status, desk counts;
    - per-department stores (`@Observable`), which cache by import stamp and reload with `.task(id:
      importStamp)`;
    - the SSE event client, the Keychain store, routing (`AppRoute: Codable, Hashable`), the unknown-last
      comparator and formatters.
  - **PennantDesign:**
    - `ClaimText`, `ClaimValue` (help tag, popover, pin), `BasisPopover`, `EvidenceView`;
    - `RankStrip`, `RangeBar`, `SeverityBadge`, `Masthead`/`Scoreboard`, `ReportCard`, `ReportSection`;
    - table helpers (`ClaimTable`, column customization persistence), chart styles (range bands, most-likely
      rules, hatched thin evidence);
    - club theming and tone colours;
    - `#Preview`s fed by fixtures.
  - **PennantFeatures**, one target per department: FrontOffice, MajorLeague, Farm, Scouting, Trades, Finance,
    Medical, League, Philosophy, Player, StaffRoom, Setup. Each feature exports a `DepartmentModule`:

    ```swift
    protocol DepartmentModule {
      static var id: DeptID { get }; static var title: LocalizedStringResource { get }
      static var symbol: String { get }; static var order: Int { get }
      static var views: [DepartmentViewDescriptor] { get }       // id, title, symbol, keywords, view builder
      static func badge(from summary: FrontOfficeSummary) -> Int?
    }
    ```

    The app target assembles the registry. From it come the sidebar, the Go menu, the command-palette and
    search results, the Spotlight shortcuts and the default windows. **Adding a function means adding a view
    descriptor; adding a department means adding a module.**
- **App target:** scenes, commands, Sparkle (`SPUStandardUpdaterController`, consent-first, automatic
  updates off), notifications (`UNUserNotificationCenter`), the dock badge (`NSApp.dockTile.badgeLabel`),
  App Intents (`AppEntity` for players and clubs, `IndexedEntity` with `CSSearchableIndex` for Spotlight,
  `AppShortcutsProvider`), and backups.
- **Widget extension:** the record and next game, and the desk (WidgetKit, macOS desktop widgets). Data is
  shared through the App Group **`<TEAMID>.group.com.dakotawise.pennant`**; the Team-ID prefix avoids the
  macOS 15+ prompt. The app writes a small JSON snapshot after each refresh, and the widget never calls the
  server.
- **Rules for Swift code** (in `.claude/rules/macos.md`):
  - No baseball thresholds, no ranking, no copy beyond structural labels (menu and tab names in a String
    Catalog).
  - A number shown is a number served.
  - A script scans the String Catalog with the same banned-jargon list.

## 7. Coexistence and the way back

The rebuild is one big rewrite, but it is built so that *any* point can be abandoned without loss.

1. **Restore point** (the owner approved it on 2026-09-25; created and pushed at N0 the same day):
   - an annotated tag **`pre-swiftui`** on `87934cf`;
   - branch **`archive/electron-react`** at the same commit;
   - both pushed to `origin`.
2. **Where the work happens:**
   - **All work is on `feature/swiftui`**, with milestone PRs stacked into it. `main` isn't touched until the
     owner approves the final merge.
   - `main` keeps taking server-only work, merged into the branch weekly.
3. **The React/Electron app keeps working on the branch** until the cutover PR, which is the *last* PR and
   deletes `src/`, `electron/`, the web tests and the web dependencies. Reverting that one PR restores them.
4. **Data compatibility:**
   - Both apps use the same data folder.
   - Server changes are **additive only**: new tables such as `report_snapshots`, `desk_items`, `following` and
     `standings_snapshots` in `history.db`, and new files. Nothing existing is altered, and the old app ignores
     them.
   - The watchlist's migration into `following` **copies** it and doesn't move it.
   - The data-folder lock stops the two apps running together.
5. **Backup before first run:** the first time the Mac app starts on a data folder, it copies `history.db` (the
   irreplaceable rating history), `settings.json`, `config.json` and `credentials.json` into
   `backups/pre-swiftui-<date>/`.
   - `league.db` (1.28 GB) is re-importable and isn't copied.
   - A Settings button restores the backup.
6. **Identities:**
   - Development builds are `com.dakotawise.pennant.dev` ("Pennant Dev"), so they can sit beside anything.
   - The release app uses `com.dakotawise.pennant`. No Electron installer was ever published, so D-049's hold
     on the app id is not at risk.
   - Keychain items are new (`com.dakotawise.pennant.apikeys`). An optional one-time "Import key from the
     Electron app" button can come later; otherwise the key is re-entered once.
7. **Rolling back:**

   ```bash
   git switch archive/electron-react
   ```
   ```bash
   npm ci && npm run desktop
   ```

   Then, if needed, Settings ▸ Restore backup (or copy `backups/pre-swiftui-*/history.db` back). This procedure
   is recorded in DEVELOPMENT.md at N0.

## 11. Risks and how they are handled

| Risk | Handling |
|---|---|
| Rewrite fatigue: a long branch with nothing shippable | N6 gives a usable Morning Report on the real save early; every milestone runs; the React app keeps working until the end |
| Moving about a quarter of the UI copy server-side is large | Done per department in the milestone that ports it; jargon tests catch regressions; `Row` and `Cell` keep the moved copy simple |
| SwiftUI `Table` limits (expandable rows, very custom cells) | `OutlineGroup` / `List(children:)` for hierarchies, and a disclosure row pattern; drop to `NSTableView` via `NSViewRepresentable` only if a measured need appears |
| Hover-to-explain isn't Mac-idiomatic | Help tag on hover, popover on click or Space, inspector on pin (section 3.3). Verify with the owner at N5 using a real build |
| Glass legibility and performance | Glass on chrome only; custom glass in containers; test Reduce Transparency and Increase Contrast; Instruments at N15 |
| Signing, notarization and privacy prompts | Developer ID from N3 for dev signing, and full notarization by N14; usage strings in Info.plist; no sandbox |
| Sidecar crash or hang | Supervised restarts, a logged server, and a clear unavailable state; the kill-mid-import check at N1 |
| Contract drift between TypeScript and Swift | Generated client, committed spec, drift test, `swift build` in CI |
| Branch drift against `main` | Weekly merges; server changes additive; `main` takes server-only work |
| Verifying visuals without watching the screen | XCUITest screenshots and `ImageRenderer` PNGs reviewed each milestone; the owner reviews real builds at N5, N6 and N8 |
| An API is new in macOS 27 while the minimum is 26 | Only behind `#available`, with a macOS 26 path that still reads well |
